## 🚀 Conventional Commit Structure

The basic structure ensures every commit clearly states its purpose:

| Component | Example | Description |
| :--- | :--- | :--- |
| **Type** | `feat`, `fix`, `chore` | The main category of the change. |
| **Description** | `add user login validation` | Short, descriptive summary of the change. |
| **Footer** | `Co-authored-by: <name>` & `#branch-number` | Mandatory author/branch details. |

## 🛠️ Commit Workflow Steps

Follow these steps when prompted by the **Conventional Commits** extension:

### Step 1: Select Type (`type`)
Choose the most accurate commit type (e.g., **`feat`** for a new feature, **`fix`** for a bug correction, **`chore`** for maintenance/config).

### Step 2: Select Emoji
Select an emoji that visually represents the chosen type (e.g., ✨ for `feat`, 🐛 for `fix`).

### Step 3: Scope (`scope`)
**Ignore this step.** Do not enter any value for the scope.

### Step 4: Write Short Description (Subject)

Write a short (max 50-70 characters) and descriptive subject line. This line **must** be terminated with the branch number, and co-author info if pair-programming (note that co-author must me referenced by github-name):

* **Solo Commit:** `Your descriptive subject #branch-number`
    * *Example:* `fix: correct typo in service API #21`
* **Pair Programming:** `Your descriptive subject (Co-authored-by: GitHub-handle) #branch-number`
    * *Example:* `feat: implement user authentication flow (Co-authored-by: awesome-coder) #33`

### Step 5: Write Long Description (Body)

Provide a longer description if the subject line is insufficient. **Use this section to justify major decisions or clarify ambiguous code choices.**

### Remaining Steps
For the rest of the steps (`Breaking Change`, `Issue No.`, etc.), you can typically press **Enter** or skip, unless you are deliberately making a backwards-incompatible change. This is because issu no. is already stated earlier in the commit message.
